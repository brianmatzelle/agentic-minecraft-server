# stream — TV channels + YouTube on the jumbotron 📡

**Do `$ARGUMENTS`** (repo root; compose dir `apps/server/`). Chain (since 2026-07-23, c9b149c):
feed → ffmpeg in mc-stadiumcast (4fps faces / 3fps VOD, 542×456 h264 → mpegts over a FIFO) → sanjuuni `-T` → ws://stadiumcast:8177 → `termtv.lua` on computer 10 → the same frame blitted to all 4 faces, + DFPWM audio on :8179.
Camera mode instead has sanjuuni listen on :8180 for the garviscam push. The same loop runs a SECOND leg for the small TV (computer 12, :8182/:8183). **One program, `termtv.lua`, runs every set** (it replaced `jumboplay.lua` on 2026-07-25); a set's own `/tv.conf` says which leg it attaches to. Full arch: `.claude/skills/cc/examples/jumbotron/README.md`; camera/body ops = `/jumbotron`.

## Switch the channel
- YouTube: `docker exec mc-stadiumcast /opt/source.sh youtube "<url>"` — resolves the link with yt-dlp FIRST and exits non-zero (leaving the current channel alone) if it won't play; prints `source -> youtube ▶ <title>`. Any yt-dlp-supported site works from the CLI, not just YouTube. A finished video loops.
- **Any TV channel** (~10.5k, iptv-org): `docker exec mc-stadiumcast /opt/source.sh channel "sky news"` — takes a channel id or a name, resolves it against the catalog, ffprobe-vets the stream, and only then flips; prints `source -> channel ▶ <label>`. A dead/geo-blocked pick exits non-zero with the reason and **leaves the current channel playing**.
- Bloomberg: `docker exec mc-stadiumcast /opt/source.sh bloomberg` (its own pinned feed + `BLOOMBERG_URL` override; `channel bloomberg` goes through the catalog instead)
- Camera back: `docker exec mc-stadiumcast /opt/source.sh live`
- State file `/media/source` (`<mode>[ <url>]`, persists across restarts; no file = live) + `/media/now-playing` (title). The entrypoint loop swaps the pipeline within ~5s; jumboplay reconnects on its own — nothing to do on the CC side.

## The in-game channel picker (every set, since 2026-07-25)
`termtv.lua` runs the picker next to the video and audio loops, on the computer's own terminal: ↑↓/PgUp/PgDn, `enter` tunes, `/` searches the whole catalog, `esc` back to the curated grid, `c` = camera, `m` mute, `-`/`=` volume, `[`/`]` A/V sync, `r` reload + rescan speakers, `q` quit. Header shows what's on + the measured draw-rate; a 2s tick re-reads `/now`, so a tune from chat or the CLI shows up there too.
**Touch guide (optional):** a monitor becomes a tappable channel board (tap a row to tune, bottom row = camera, top rows = reload) only when you name it — `guide=monitor_7` in that computer's `/tv.conf`. It is deliberately NOT auto-detected: the previous "odd size = guide" rule ate faces off the wall (see the sizing landmine in the README). **Touch path is untested in-world as of 2026-07-25.**
Catalog/control API = `channels.js` in mc-stadiumcast on `:8178` (internal only): `/channels` `/search?q=` `/tune?id=|?mode=live` `/now` `/health` `/refresh`. Check it: `docker exec mc-stadiumcast curl -s localhost:8178/health`. Drive the picker remotely (this is how it was verified): `apps/server/garvtunnel/cc -i 10 'os.queueEvent("key", keys.down, false)'` then the same with `keys.enter`.

## Players do it themselves, in-game
Anyone can paste a link at Garvis in Minecraft chat: `!g put https://youtu.be/… on the jumbotron` (the bare link works too). Also `!g put sky news on the jumbotron` / **any channel name** — `!g switch the jumbotron to cnbc asia`, `!g jumbotron: cgtn` — plus `!g bloomberg on the jumbotron` / `!g put the camera back on the jumbotron`.
The name is peeled out of the sentence by regex in `parseChannelAsk` (no classifier call), sanitised, and handed to `source.sh channel` as fixed argv; the catalog does the fuzzy matching. Pronouns are refused deliberately ("put *that* on the jumbotron" → null, so it falls through to the normal intents). A name that matches nothing comes back to the player as `No luck with "<x>" — no channel matching "<x>"` and changes nothing.
Path: `apps/garvis-bot/src/jumbotron.js` — a deterministic fast path in `onInGameMessage` (NO classifier call, checked before every other intent), which normalises the link to a canonical watch URL from a validated 11-char video id and fixed-argv `docker exec`s source.sh. Kill switch `GARVIS_INGAME_JUMBOTRON=off` in `apps/garvis-bot/.env` + `systemctl --user restart garvis-bot`.
Deliberately NOT wired into the paid stream-chat path (`streamchat.js`) — tollbooth buyers get body+TV only.

## Status / verify
- Frame counter: `docker exec mc-stadiumcast sh -c 'tr "\r" "\n" < /media/live.log | tail -1'` — ADVANCING = a screen is connected and drawing. **It is the ENCODE counter, not the draw rate**, and in `-T` mode the encoder only steps when the client sends *something*, so its "N fps" is really "how fast the client is asking".
- **What the screen is really doing** — ask the screen, since nothing in the container can see a blit: `apps/server/garvtunnel/cc -i 10 'local f=fs.open("/tv.stat","r") local s=f.readAll() f.close() return s'` → `Bloomberg fps=4.66 drawn=620 screens=4 feed=271x152 face=271x152 audio=playing gaps=0 vol=3.0 sync=16`. termtv rewrites it every 20 frames. `fps` is the number to pace `CHANNEL_FPS`/`TERMTV_FPS` against — but it is averaged from when the socket opened, so read it ~1fps high right after a reconnect (the client is draining the encoder's buffer) and trust only a settled connection. `feed=` ≠ `face=` means this leg's `W/H` no longer matches the wall (letterboxed or cropped, never an error); `gaps` climbing = the audio buffer is too shallow for this channel.
- **Nobody watching = 0 procs, and that is HEALTHY.** Since the 2026-07-24 leak fix the pipeline duty-cycles: up ~30s to offer a connection, and if no ws client attaches it tears down and parks 45s (an unwatched `-T` sanjuuni frees nothing and grew to 94 GiB RSS, taking the host down). So with an empty stadium the normal signature is BOTH procs absent, `[cast] no viewer after 30s — parking the feed` repeating in live.log, and the pull log ending in `Broken pipe` / `Error writing trailer` — that is the last probe window's teardown, not a crash. **Don't escalate on it.** The feed lights up within ~45s of a player looking at the screen (termtv retries every 3s).
- Viewer state: `docker exec mc-stadiumcast sh -c 'tr "\r" "\n" < /media/live.log | grep "\[cast\]" | tail -5'` — `no viewer`/`viewer left` = parked; silence + an advancing frame counter = someone is watching.
- What's up: `docker exec mc-stadiumcast sh -c 'cat /media/source; cat /media/now-playing'`.
- Pull logs: `/media/youtube.log` (yt-dlp + ffmpeg) · `/media/bloomberg.log`. "corrupt input packet" / "timestamp discontinuity" on a live feed is normal live-edge noise, not failure.
- Procs: `docker exec mc-stadiumcast sh -c 'pgrep -x sanjuuni; pgrep -x ffmpeg'` — with a viewer attached, pulled modes = both, live mode = sanjuuni only; with no viewer, neither (see above).

## Jumbotron blank/frozen? (escalate in order)
0. **Is anyone actually watching?** If the report is "it looks dead" from the CLI rather than from a player standing at the screen, stop — see the duty-cycle bullet above. Parked ≠ broken.
1. **Chunk loaded?** The jumbotron only runs while computer 10's chunk is loaded. Stadium is forceloaded since 2026-07-23 (`forceload add -970 -170 -920 -130`, 11 chunks; check: `docker exec mc-neoforge rcon-cli "forceload query -948 -147"`; revert = `forceload remove` same args).
2. **Computer on?** `docker exec mc-neoforge rcon-cli "computercraft dump"` — LANDMINE: it reports computer 10 out at ~(20481030, 133, 20485130). That is NOT a stolen computer and not a display bug. The jumbotron hangs from a **Create rope**, which makes it a **Sable** moving structure (`sable-neoforge`, "interactive moving block structures with physics" — the library under Create Aeronautics), and Sable keeps a structure's blocks in a far region of the plain overworld while simulating them at the structure's real position. `data get block 20481030 133 20485130` returns ComputerId 10, and a geo-scan at radius 4 finds the monitors, cables and speaker with it. The projection carries rendering, interaction **and sound** — the speaker up there is heard at the seats. What it does NOT carry is raw block-position queries: computer 10's player detector reports 0 players within 64 whoever is at the stadium, because it is asking about the empty far region. Don't mistake that for an audio test (we did, and got the speaker story wrong for a day). Boot it remotely: `rcon-cli "computercraft turn-on 10"`.
3. **termtv running?** `apps/server/garvtunnel/cc -s` should list id 10. Restart the player: `cc -i 10 'os.queueEvent("cc_stop")'` then `CCDEPLOY_ID=10 ccdeploy .claude/skills/cc/examples/jumbotron/termtv.lua /termtv.lua termtv`. Rollback if a change to termtv breaks the faces: `/jumboplay.lua` is still on computer 10's disk (video only, no sound, 3-4fps).
4. **Whole layer:** `docker compose restart stadiumcast` — resumes whatever `/media/source` says.

## A link won't play
- The error the player/CLI sees is yt-dlp's own last line. `Video unavailable` / `Private video` / age-gated → nothing to fix, try another link.
- **`Sign in to confirm you're not a bot`** = YouTube's IP bot-check tripped. Fix: export a Netscape cookies jar from a logged-in browser to `apps/server/stadiumcast/media/cookies.txt` (bind-mounted, gitignored) — `ytdlp-args.sh` picks it up automatically, no rebuild.
- Widespread breakage = stale yt-dlp. It self-updates once on a failed resolve; force it with `docker exec mc-stadiumcast yt-dlp --update-to nightly`.
- The container needs egress: `docker exec mc-stadiumcast yt-dlp --version` then a probe, e.g. `docker exec mc-stadiumcast ffprobe -v error -show_entries stream=codec_name -i "<url>"`.

## TV audio — stadium speakers (since 2026-07-25)
Second, independent leg: its own ffmpeg pulls the **same** url the video leg chose (`/media/audio-source`, written by `pull_to_sanjuuni`) → DFPWM (1 bit/sample, 6 KB/s) → `castaudio.js` ws on `:8179` → whichever computer holds the speakers → CC speakers. `termtv.lua` on computer 10 takes that socket today; `jumboaudio.lua` is the standalone alternative for a speaker-only computer.
- **A speaker on computer 10 IS heard at the seats** (owner confirmed 2026-07-26), even though the computer's blocks sit 20M blocks out in the overworld — Sable simulates the structure at the stadium and that carries sound too (see the Sable landmine above). Don't repeat the 2026-07-25 mistake of "proving" otherwise with computer 10's player detector: it reports 0 players within 64 of the far region no matter who is at the stadium, so that test is not evidence about audio. If you ever do want the speakers on their own computer (e.g. to spread them around the seats), that still works: `CCDEPLOY_ID=<id> ccdeploy .claude/skills/cc/examples/jumbotron/jumboaudio.lua /jumboaudio.lua jumboaudio` plus `audio=off` in computer 10's `/tv.conf` — one audio client per leg, see below.
- **One audio client per leg**: castaudio.js pops a shared ring (`ring.shift()`), so two connected sets would each get every other second. termtv skips the socket entirely when it has no speaker attached, for exactly this reason.
- Health: `docker exec mc-stadiumcast curl -s localhost:8179/health` → `{up, queued, target, primed, produced, served, skipped, underruns, clients, src}`. Log: `/media/audio.log`.
- **Read it like this:** `up:false` + empty `src` = the video pipeline is down/parked, so audio is idle (correct, not broken). `clients:0` = no speaker computer attached. `underruns` climbing = the buffer is too shallow, raise `CAST_AUDIO_DELAY`. `skipped` jumping at startup is the live-edge re-anchor doing its job.
- **`served` frozen while `clients:1` = the CC side has parked, not the pipeline.** Two health reads ten seconds apart is the whole diagnosis — a healthy set climbs ~1/s (and `queued` drifting up to `RING_MAX` with nobody asking is the same story from the other end). Cause found 2026-07-26: **mute wedged the sound until termtv was restarted** — `speaker.stop()` (which `m` calls) discards the queued audio whose hand-off fires `speaker_audio_empty`, so the `playAudio` retry waited for an event that could never come, and the audio coroutine parked *permanently*; unmute flipped the flag with nothing left to read it. Fixed in `termtv.lua` + `jumboaudio.lua` by bounding that wait (0.5s re-check, 6s = stuck → `stop()` + drop the chunk, shown as `spk-stall` on the status line). If a set is ever silent with `served` frozen, `cc -i <id> 'os.queueEvent("cc_stop")'` + `ccdeploy` brings it back; reproduce the failure mode with `cc -i 10 'peripheral.call("right","stop")'` a few times and watch `served`.
- In-game (at the speaker computer): `m` mute, `-`/`+` volume (0-3; volume also sets RANGE), `[`/`]` A/V sync in 1s steps, `r` rescan speakers, `q` quit.
- Knobs on the stadiumcast service in compose: `CAST_AUDIO: "0"` mutes the stadium at the source; `CAST_AUDIO_DELAY` (**16** since 2026-07-25 — 8 was shallower than Bloomberg's ~10s segments and logged 68 gaps in 10 minutes) is buffer depth AND A/V offset; `CAST_AUDIO_FILTER` (default `dynaudnorm=f=250:g=15`) evens out channel-to-channel loudness — worth keeping, since 1-bit audio punishes quiet sources.
- Quality is deliberately lo-fi: mono, 1-bit, 48 kHz. It sounds like a stadium PA.

## termtv — the TV program, on every set (since 2026-07-25)
One file, `termtv.lua`, runs both the stadium jumbotron (computer 10, four faces) and the small TV out in the world (computer 12, one monitor + speaker): video, sound and the channel remote as three coroutines on the computer's own terminal (enter tune, `/` search, `c` camera, `m` mute, `-`/`=` volume, `[`/`]` A/V sync, `r` reload + rescan speakers, `q` quit). Same tuned channel everywhere — `/media/source` is one global "what's on", so tuning at either set flips the other.
- **Hardware is auto-detected**: EVERY monitor plays (all faces show the SAME frame — the jumbotron is the sides of one cube), every speaker in reach = the PA. Screens needn't match each other or the feed — each shows the centre, cropped or letterboxed. **After a wall rebuild**: relaunch termtv so it rescans (peripheral names change — the faces are `monitor_12..15` since 2026-07-26), then match the feed to the new size, `CAST_W/H = cols*2 x rows*3` (542x456 today) — `feed=` vs `face=` in `/tv.stat` is the only way to see a mismatch, since it letterboxes silently instead of erroring. **The only per-set config is `/tv.conf`** on that computer's disk — `video=`/`audio=` ws urls, plus optional `ctl=`, `scale=`, `guide=`, `audio=off`. No file = the small-TV leg, so a brand-new set needs no config. Computer 10's is two lines pointing at `:8177`/`:8179`. Read one: `cc -i 10 'local f=fs.open("/tv.conf","r") local s=f.readAll() f.close() return s'`.
- **A leg of the pipeline per set**: `cast_loop` in `entrypoint.sh` runs TWICE. Small TV = 158x114 (79x38 chars at 0.5 textScale), video ws **:8182**, audio ws **:8183**, fifo `/tmp/termtv.ts`, log `/media/termtv.log` + `/media/termtv-audio.log`, source hand-off `/media/termtv-source`. Own ffmpeg, own sanjuuni, own park cycle (20s/20s, vs the jumbotron's 30s/45s) — a viewer at one screen cannot stall the other.
- Health: `docker exec mc-stadiumcast curl -s localhost:8183/health` (same shape as :8179) · `docker exec mc-stadiumcast sh -c 'tr "\r" "\n" < /media/termtv.log | tail -3'` for the frame counter · `grep "^\[termtv\]" /media/termtv.log` for park/rebuild history. Both legs' `[cast]`-style lines are now prefixed with the leg name (`[jumbo]` / `[termtv]`).
- Deploy/refresh: `CCDEPLOY_ID=12 .claude/skills/cc/scripts/ccdeploy .claude/skills/cc/examples/jumbotron/termtv.lua /termtv.lua termtv`. Autostart lives in `/startup.lua` on the computer (from `termtv-startup.lua`) — **required**, because the set's chunk unloads when nobody is nearby and that reboots the computer.
- Compose knobs (stadiumcast service): `TERMTV: "0"` removes the small-TV leg · `CAST_W/H` (542x456, the jumbotron wall) and `TERMTV_W/H` (158x114) should each match that set's monitor at 0.5 textScale (`cols*2` x `rows*3`, even numbers) or the picture is centred and cropped/letterboxed — termtv prints the mismatch in its status line and in `/tv.stat` · `TERMTV_FPS` (8) and the jumbotron's `CHANNEL_FPS` (**4**) must each stay UNDER what that screen really draws, see the pacing gotcha and read the real rate from `/tv.stat` · `TERMTV_AUDIO_DELAY` (8) and `CAST_AUDIO_DELAY` (16) are the per-leg A/V offsets · `TERMTV_LIVE_URL` = how camera mode reaches the small screen.
- **Camera mode goes the long way round**: only one process can hold garviscam's :8180 push, so termtv pulls the camera from Owncast's HLS instead (`http://owncast:8080/hls/0/stream.m3u8`). That means camera-on-termtv works only while the web stream is actually live, WITH game audio, ~10s later than the stadium. Web stream down = Owncast serves its "stream offline" slate and that is what the TV shows.
- A second screen means a second pull of the same channel (and a second yt-dlp resolve in youtube mode) — cheap for HLS, but that is why each leg can land on a *different* ranked variant of the same channel.
- **Buffer depth has to clear the channel's SEGMENT period, and that varies per channel.** The default 8 suits the ~6s segments most iptv-org feeds use; Bloomberg's own manifest ships **~10s** segments (watch `produced` jump by 10 at a time in the health JSON while `queued` troughs at 3), which leaves only ~3s of margin — one late segment there is an audible gap. Press `]` a few times at the set (or raise `TERMTV_AUDIO_DELAY`) when a channel stutters. `underruns` is cumulative and never resets, so read it as two samples: frozen = fine, climbing = too shallow. Every tune and every park re-primes the buffer, so a session of channel-surfing legitimately racks up a dozen of them.

## Gotchas
- **`[jumbo] pipeline (channel) exited, restarting in 3s` on a loop = the SCREEN hung up, not the feed.** sanjuuni `-T` serves one client and exits when it leaves, taking ffmpeg down with it (`WebSocket exception: I/O error: Broken pipe` in live.log, `Error writing trailer: Broken pipe` in channel.log), and every rebuild is a blank-and-relight on the faces plus an audio re-prime. The cause was termtv's frame `ws.receive()` timeout being shorter than the feed's SEGMENT period — a screen that drains a segment then waits ~10s on the encoder timed out and reconnected. `RECV_TIMEOUT` in termtv.lua is 20s for exactly this; don't lower it toward the frame interval, it has nothing to do with framerate.
- **The RSS climb is sanjuuni keeping every frame it ever encoded** (`frameStorage[frame] = ""` frees the length, not the capacity — `sanjuuni.cpp:277`), measured ~96MB/min at 4.4fps with the client keeping up and skipping nothing. Nothing on the CC side can slow it; the park cycle and `CAST_MAX_RSS_MB` recycle are the guards. A 1-line patch to our own source build (`std::string().swap(frameStorage[frame]);`) would end it — **not done**.
- stadiumcast scripts (`entrypoint.sh`, `source.sh`, `ytdlp-args.sh`, `channels.js`) are BAKED into the image — rebuild after edits: `docker compose build stadiumcast && docker compose up -d stadiumcast`.
- The catalog index build is a SHORT-LIVED child process on purpose: the upstream JSON is ~15MB and parsing it peaks at a few hundred MB, and this container is capped at `mem_limit: 2g` shared with sanjuuni's frame store (which killed the host once). Don't "optimise" it into the long-running serve process.
- Channel URLs are re-resolved AND re-probed every supervisor loop (`channels.js url <id> --probe` — top 3 ranked variants probed concurrently, best one that answers wins, ~5s). A variant dying mid-play heals into the next-best on its own.
- **"I picked a channel and the screen didn't change" = probably an ad slate, not a frozen jumbotron.** ffprobe only proves there's decodable video; a Pluto TV bumper (`jmp2.uk/plu-…`) or an idle per-event feed (`*-event.m3u8`) passes and renders as a near-static dark frame that looks exactly like a freeze. Diagnose by grabbing the actual frame: `docker exec mc-stadiumcast sh -c 'URL=$(node /opt/channels.js url <id> | cut -f1); ffmpeg -y -i "$URL" -frames:v 1 /media/peek.png'` then `docker cp mc-stadiumcast:/media/peek.png /tmp/peek.png` and look at it. Fix belongs in `rankStreams` (labelled quality beats unlabelled, non-event beats event, then nearest 720p, then upstream order) — not in the probe, which cannot tell content from slate.
- Some CDNs 403 without the stream's own `user_agent`/`referrer`; those are carried from the catalog into ffmpeg as input options. termtv drops them, which is why a few channels work here that don't there.
- The monitor faces are silent by design — sound comes from CC **speakers** on a separate computer, see "TV audio" above. `live` (camera) mode has no audio AT THE STADIUM: garviscam's :8180 push is video only, its game audio goes to Owncast. termtv gets camera audio anyway, because it takes that mode from Owncast's HLS instead.
- **Pacing**: the faces really draw 3-4fps (5 monitors × 164×81 blit/frame, server-tick bound). A live feed self-corrects when the encoder outruns that (the HLS demuxer skips to the live edge); a VOD can't, so encoding above the draw ceiling turns into slow motion via backpressure. Hence `YT_FPS=3` + ffmpeg `-re` for pulled files — encode just UNDER the ceiling and let `-re` be the clock. Override per-service with `YT_FPS`/`YT_FORMAT` env.
- The ffmpeg→sanjuuni hop is a FIFO (`/tmp/cast.ts`), not a socket, because restarting a TCP hop within ~60s died on TIME_WAIT ("Connection refused" every time a VOD ended). Don't "simplify" it back to a port.
- googlevideo URLs expire (~6h) — ffmpeg exits, the supervisor re-resolves. Expect a few seconds of black on a long-running video.
- Bloomberg/YouTube modes need no camera: garviscam's :8180 push just gets connection-refused and retries forever (harmless).
- `live` mode shows nothing while garviscam is down. As of 2026-07-23 garviscam is deliberately STOPPED (Secret Base Trainer/Sable StackOverflowError crashes fresh-joining clients; the crash screen was spamming tv.starting.cc) — `docker compose start garviscam` once that bug is fixed. See /jumbotron + minecraft-server-operational-state memory.
